Rappel : un agent appelle des outils

Le modèle ne fait que demander l’appel : c’est l’application qui exécute, contrôle les permissions et valide les arguments.

Rappel du cours précédent : un agent LLM = LLM + outils + mémoire + boucle. Les étapes 2 à 6 peuvent se répéter. Insister sur le point 3 : la sortie du modèle est une donnée structurée, jamais une exécution. Tout ce qui suit dans le cours standardise les flèches 2, 4 et 5.

Le problème : N × M intégrations

Même raisonnement que LSP pour les éditeurs de code : un contrat commun découple ceux qui consomment de ceux qui exposent.

Sans standard, chaque application réécrit pour chaque service le contrat, l’authentification, le format des résultats. Language Server Protocol (2016) a résolu le même problème entre éditeurs et langages ; MCP s’en inspire explicitement, jusqu’au choix de JSON-RPC. Question à poser à la salle : qu’est-ce qui, dans un connecteur, est réellement spécifique ?

Framework, protocole, implémentation

Framework

Construit et orchestre les composants d’une application agentique.

Mastra, LangGraph, AutoGen.

Protocole

Fixe les règles d’échange entre composants indépendants.

MCP, A2A.

Implémentation

Réalise le protocole dans un langage donné.

SDK TypeScript, Python, Java…

Un protocole ne dit rien de l’orchestration interne : deux agents écrits avec des frameworks différents peuvent interopérer.

Confusion fréquente : « MCP ou LangGraph ? » n’a pas de sens, ce ne sont pas des objets de même nature. Les frameworks vus au cours précédent savent tous consommer des serveurs MCP ; plusieurs savent exposer un agent en A2A.

D’où viennent ces protocoles ?

  • Le besoin d’interopérabilité date des SMA classiques : seul l’encodage a changé.
  • Les deux protocoles sont des standards ouverts, portés par une fondation et non par un éditeur.
  • Ils évoluent vite : toujours citer la révision de la spécification utilisée.
Lien avec la slide « De FIPA ACL à MCP et A2A » du cours précédent. FIPA ACL exigeait des ontologies partagées ; ici le langage naturel et les schémas JSON jouent ce rôle. A2A a été confié à la Linux Foundation en juin 2025, MCP à l’Agentic AI Foundation (fonds de la Linux Foundation) en décembre 2025. Les dates de version sont à revérifier avant chaque séance.

Deux axes d’intégration

« A2A connecte les agents entre eux ; MCP connecte chaque agent à ses propres outils. » — documentation A2A

C’est la carte mentale de tout le cours. MCP : relation asymétrique entre une application et une capacité qu’elle pilote. A2A : relation entre pairs autonomes, chacun gardant ses outils et sa logique privés. La frontière est parfois floue, on y revient en partie 3.

01MCP
Accéder à des capacités

Model Context Protocol : relier une application IA à des outils, des données et des consignes.

Partie la plus longue, environ 30 min. Progression : architecture et rôles, primitives, contrat d’outil, cycle d’un appel et messages JSON-RPC, évolution de la spécification, transports, puis sécurité et limites. Rappeler la carte des deux axes : on traite ici l’axe vertical.

Architecture : hôte, clients, serveurs

Un client = une relation avec un serveur. Les serveurs ne se voient pas entre eux : seul l’hôte agrège.

Exemples d’hôtes : un IDE, un assistant de bureau, un agent Mastra. Le client est un composant de l’hôte, pas un programme séparé. Un serveur MCP n’a pas besoin de LLM : c’est souvent un simple adaptateur au-dessus d’une API existante. L’isolation entre serveurs est une propriété de sécurité : un serveur ne lit ni la conversation complète ni les autres serveurs.

Qui fait quoi ?

RôleResponsabilitésNe fait pas
HôteDialogue avec l’utilisateur et le LLM, agrège le contexte, applique les permissions et le consentement.Parler MCP directement : il délègue à ses clients.
Client MCPDécouvre les capacités d’un serveur, transmet les appels, reçoit résultats et notifications.Décider quel outil appeler.
Serveur MCPPublie ses capacités, valide les entrées, exécute l’opération avec ses propres contrôles d’accès.Voir la conversation ou piloter le modèle.

La découverte ne confère aucun droit : l’hôte et le serveur contrôlent chacun de leur côté.

Point d’attention niveau master : la décision d’appeler un outil est prise par le LLM, mais la décision d’exécuter l’appel est prise par l’hôte. Ce découplage est ce qui permet le « human in the loop ».

Trois primitives, trois pilotes

PrimitiveRôleQui décide de l’utiliser ?Exemple documentaire
ToolExécuter une action ou un calcul.Le modèle, sous contrôle de l’hôte.chercher_document("authentification")
ResourceLire une donnée identifiée par une URI.L’application hôte.docs://securite/auth

  • Méthodes : tools/list · tools/call, resources/list · resources/read, prompts/list · prompts/get.
  • Un prompt MCP renvoie des messages, pas une réponse générée.
La colonne « qui décide » est la clé de lecture de la spécification : model-controlled, application-controlled, user-controlled. En pratique, la majorité des serveurs n’exposent que des tools. Une resource peut être du texte ou du binaire ; son URI n’est pas forcément une URL HTTP.

Même service, deux interfaces

Extraits TypeScript côté serveur · fonction métier commune chercherDocument.

API HTTP · Express

import express from 'express';
import { chercherDocument } from './recherche.js';

const app = express();
app.use(express.json());
app.post('/recherche', async (req, res) => {
  const result = await chercherDocument(req.body);
  res.json(result);
});
app.listen(3000);

Serveur MCP · SDK TypeScript v2

import { McpServer } from '@modelcontextprotocol/server';
import { serveStdio } from '@modelcontextprotocol/server/stdio';
import * as z from 'zod/v4';
import { chercherDocument } from './recherche.js';

serveStdio(() => {
  const server = new McpServer({ name: 'docs', version: '1.0.0' });
  server.registerTool('chercher_document', {
    description: 'Recherche dans le catalogue',
    inputSchema: z.object({ requete: z.string() })
  }, async (args) => ({ content: [{ type: 'text',
    text: JSON.stringify(await chercherDocument(args)) }] }));
  return server;
});

Même résultat métier. Côté MCP, le nom, la description et le schéma sont découvrables à l’exécution par n’importe quel client compatible.

Les exemples supposent une fonction métier et les dépendances installées. Une API peut publier un contrat OpenAPI ; la différence tient à la découverte à l’exécution et au cycle d’intégration standardisé, pas à une supériorité technique. Extraits pédagogiques : pas de gestion d’erreur ni de validation côté Express. Le SDK v2 (@modelcontextprotocol/server) implémente la révision 2026-07-28 ; le paquet v1 @modelcontextprotocol/sdk s’arrête à 2025-11-25. serveStdio reçoit une fabrique de serveurs : il sert un client récent (server/discover) comme un client de l’ancienne génération (initialize). Un server.connect(new StdioServerTransport()) ne servirait que l’ancienne génération.

Un contrat d’outil

{
  "name": "chercher_document",
  "description": "Recherche dans le catalogue
     interne. Renvoie au plus 10 documents.",
  "inputSchema": {
    "type": "object",
    "properties": {
      "requete": { "type": "string" },
      "limite":  { "type": "integer",
                   "maximum": 10 }
    },
    "required": ["requete"]
  }
}
  • name : identifiant utilisé dans tools/call.
  • description : lue par le modèle. C’est du prompt, à écrire et à tester comme tel.
  • inputSchema : JSON Schema ; contraint la forme des arguments.
  • Optionnels : outputSchema, annotations (lecture seule, destructif…).

Élément de la réponse à tools/list. Le schéma ne garantit ni l’exactitude du résultat ni les droits d’accès.

Faire le lien avec les « Principled Instructions » du cours précédent : la qualité des descriptions conditionne la qualité des appels. Les annotations sont des indications fournies par le serveur : un hôte ne doit pas leur faire confiance si le serveur n’est pas de confiance.

Cycle complet d’un appel

Séquence en révision 2026-07-28. Avant, l’étape 1 commençait par un échange initialize.

Comparer avec la séquence de tool calling de l’introduction : MCP standardise uniquement les flèches entre client et serveur (1, 2, 6, 7). Les étapes 3 à 5 et 8 à 9 restent du ressort de l’hôte et du fournisseur de LLM. Les étapes 4 à 8 se répètent tant que le modèle demande des outils.

Sur le fil : JSON-RPC 2.0

// Requête : client → serveur
{ "jsonrpc": "2.0", "id": 2, "method": "tools/call",
  "params": {
    "name": "chercher_document",
    "arguments": { "requete": "authentification" },
    "_meta": {
      "io.modelcontextprotocol/protocolVersion": "2026-07-28",
      "io.modelcontextprotocol/clientCapabilities": {} } } }

// Réponse : serveur → client
{ "jsonrpc": "2.0", "id": 2,
  "result": {
    "resultType": "complete",
    "content": [{ "type": "text", "text": "[{\"id\": \"doc-12\", \"titre\": \"Auth OAuth\"}]" }],
    "isError": false } }

Extraits simplifiés. id associe la réponse à la requête ; isError: true signale une erreur métier que le modèle peut lire et corriger.

Deux niveaux d’erreur à distinguer : l’erreur de protocole (objet « error » JSON-RPC, par exemple méthode inconnue) et l’erreur d’exécution de l’outil (résultat avec isError), renvoyée au modèle pour qu’il puisse réessayer. Depuis 2026-07-28, chaque requête porte sa version et les capacités du client dans _meta.

MCP évolue : 2025-11-25 → 2026-07-28

2025-11-252026-07-28 (révision courante)
OuvertureÉchange initialize / initializedAucun handshake ; server/discover à la demande
Version et capacitésNégociées une fois, au débutPortées par chaque requête dans _meta
Session HTTPEn-tête Mcp-Session-IdSupprimée : protocole sans état
Serveur → clientRequêtes initiées par le serveurRésultat input_required, puis nouvel essai du client
Dépréciés—Roots, sampling, logging

Sans état = chaque requête est autonome : mise à l’échelle et répartition de charge simplifiées. Un SDK peut prendre en charge les deux générations.

Intérêt pédagogique : montrer qu’un protocole jeune fait des choix d’architecture réversibles. Le passage au sans-état rapproche MCP d’une API HTTP classique et facilite le déploiement derrière un répartiteur de charge. Version du protocole et version du SDK sont deux choses distinctes. Clients anciens et serveurs récents ne sont pas compatibles sans prise en charge des deux générations.

Quand le serveur a besoin d’une précision

  • Élicitation : le serveur demande une information à l’utilisateur, via l’hôte.
  • Le serveur ne garde rien en mémoire entre 2 et 3 : c’est le client qui rejoue l’appel.
Mécanisme appelé « multi round-trip requests » dans la révision 2026-07-28. Il remplace les requêtes initiées par le serveur. Retenir l’idée, pas le détail des champs : on retrouve exactement le même besoin côté A2A avec l’état input-required.

Transports : local et distant

stdio

L’hôte lance le serveur comme un processus local et échange par entrée / sortie standard.

Simple, sans réseau. Le serveur hérite des droits de l’utilisateur.

Les logs vont sur stderr, jamais sur stdout.

Streamable HTTP

Le serveur est un service distant : une requête = un POST, réponse JSON ou flux SSE.

Partageable entre utilisateurs et applications.

Autorisation par OAuth 2.1 ; contrôle d’accès indispensable.

Les messages JSON-RPC sont identiques dans les deux cas. Le TP utilise stdio.

Piège classique du TP : un console.log dans un serveur stdio corrompt le flux JSON-RPC. En HTTP, le serveur MCP est un serveur de ressources OAuth : il valide un jeton, il ne gère pas lui-même les mots de passe.

Une frontière de confiance

Risques

  • Injection indirecte : un résultat d’outil contient des instructions.
  • Empoisonnement d’outil : la description elle-même est hostile, ou change après installation.
  • Trio dangereux : données privées + contenu non fiable + canal de sortie.

Mesures

  • Moindre privilège par serveur ; lecture seule par défaut.
  • Confirmation humaine pour les actions sensibles.
  • Épingler les versions, vérifier la provenance des serveurs.
  • Journaliser les appels, sans secrets.
Message central : toute sortie d’outil est une donnée non fiable, pas une instruction. Le « trio dangereux » (lethal trifecta, Simon Willison) : dès qu’un agent combine ces trois propriétés, l’exfiltration devient possible sans faille logicielle. Lien avec le défi « injection de prompt entre agents » du cours précédent. Un serveur stdio s’exécute avec les droits de l’utilisateur : installer un serveur MCP, c’est exécuter du code tiers.

Ce que MCP ne règle pas

  • Il ne remplace ni l’API métier ni son modèle d’autorisation.
  • Un schéma valide ne garantit pas un résultat exact.
  • Chaque description d’outil consomme du contexte : cent outils chargés coûtent cher avant même la première question.
  • Le choix du bon outil reste une décision du modèle, donc faillible.

Pistes actuelles : chargement des outils à la demande, recherche d’outils, exécution de code qui appelle les serveurs.

Point critique niveau master : le coût en contexte et la dégradation du choix d’outil quand leur nombre augmente sont des sujets de recherche et d’ingénierie ouverts. Une API documentée par OpenAPI reste un choix légitime quand les clients ne sont pas des applications IA.

02A2A
Déléguer entre agents

Agent2Agent : confier une tâche à un agent autonome, sans connaître son fonctionnement interne.

Environ 20 min. On passe à l’axe horizontal. Progression : découverte par l’Agent Card, objets clés, cycle de vie d’une tâche, scénario complet, puis suivi des tâches longues. Faire remarquer au fil de l’eau ce qui ressemble à MCP (JSON-RPC, découverte à l’exécution) et ce qui s’en écarte (opacité, durée).

Pourquoi un second protocole ?

Un outil

Entrée et sortie décrites par un schéma.

Appel court, le plus souvent sans état.

L’appelant garde le contrôle du raisonnement.

Un agent

Reçoit un objectif en langage naturel.

Travail long, en plusieurs tours ; peut demander une précision ou refuser.

Décide seul de la méthode : boîte opaque.

A2A standardise la délégation entre pairs : découverte, échange de messages, suivi d’une tâche dans le temps.

On peut exposer un agent comme un simple outil MCP, mais on perd alors le suivi d’une tâche longue, la négociation et les échanges multi-tours. Lien avec le Contract Net vu au cours précédent : annonce d’une tâche, acceptation ou refus, exécution, résultat.

Acteurs et découverte

La découverte passe par une URL connue, un registre ou une configuration directe.

Vocabulaire de la spécification : user, A2A client (agent client), A2A server (agent distant). L’opacité est un choix de conception : elle protège la propriété intellectuelle et permet de faire collaborer des organisations différentes. L’Agent Card est l’équivalent du Directory Facilitator de FIPA, en décentralisé.

L’Agent Card

{
  "name": "Agent d'analyse documentaire",
  "description": "Analyse des contrats, produit une synthèse",
  "version": "1.2.0",
  "supportedInterfaces": [{
    "url": "https://analyse.exemple.fr/a2a",
    "protocolBinding": "JSONRPC",
    "protocolVersion": "1.0" }],
  "capabilities": { "streaming": true,
                    "pushNotifications": false },
  "defaultInputModes": ["text/plain", "application/pdf"],
  "defaultOutputModes": ["application/pdf"],
  "skills": [{
    "id": "analyse-contrat",
    "name": "Analyse de contrat",
    "description": "Repère les clauses à risque",
    "tags": ["juridique", "synthèse"] }]
}
  • supportedInterfaces : où et comment joindre l’agent.
  • capabilities : flux, notifications.
  • skills : ce que l’agent sait faire, décrit pour un autre agent.
  • Aussi : schémas de sécurité, signature de la carte.

Trois bindings en version 1.0 : JSON-RPC, gRPC, HTTP+JSON.

Contraste avec MCP : une skill n’a pas de schéma d’entrée strict, elle décrit une compétence en langage naturel. Le client choisit un agent, pas une fonction. La carte peut être signée pour en vérifier la provenance ; une carte étendue peut être servie après authentification.

Les objets clés d’A2A

ObjetRôleÀ retenir
MessageUn tour d’échange, de rôle user ou agent.Composé de parts.
PartUn fragment de contenu : texte, fichier (octets ou URL), données JSON.Multimodal par construction.
TaskUn travail suivi dans le temps, avec identifiant et état.Créée par l’agent distant, jamais par le client.
ArtifactUn résultat produit par la tâche : rapport, fichier, données.Distinct des messages de dialogue.
contextIdRegroupe plusieurs tâches et messages liés.Fil de conversation.

À un message, l’agent distant répond soit par un Message direct, soit par une Task.

Réponse simple et immédiate : un Message suffit. Travail long ou à suivre : l’agent crée une Task. C’est l’agent distant qui choisit, le client doit gérer les deux cas.

Cycle de vie d’une tâche

Sur le fil : TASK_STATE_WORKING, TASK_STATE_INPUT_REQUIRED… Une tâche terminée n’accepte plus de message : la suite passe par une nouvelle tâche du même contexte.

Deux états « interrompus » : input-required et auth-required. Ils rendent explicite ce que le tool calling cache : un agent distant peut avoir besoin d’un humain ou d’un droit supplémentaire. Faire remarquer la parenté avec l’élicitation MCP vue plus tôt. Schéma simplifié : une tâche peut aussi échouer ou être annulée depuis un état interrompu.

Scénario : déléguer une analyse

L’agent client vérifie ensuite l’artefact : provenance, cohérence, conformité à la demande.

À aucun moment l’agent client ne voit les outils ou le raisonnement de l’agent distant. L’étape 4 réutilise le taskId pour poursuivre la même tâche. Les étapes 5 et 6 arrivent par flux ou par interrogation, voir la slide suivante.

Sur le fil : SendMessage

// Requête : agent client → agent distant
{ "jsonrpc": "2.0", "id": 1, "method": "SendMessage",
  "params": { "message": {
    "messageId": "m-001",
    "role": "ROLE_USER",
    "parts": [
      { "text": "Analyse ces trois contrats." },
      { "url": "https://exemple.fr/contrats.zip", "mediaType": "application/zip" } ] } } }

// Réponse : l’agent distant crée une tâche
{ "jsonrpc": "2.0", "id": 1,
  "result": { "task": {
    "id": "t-42",
    "contextId": "c-7",
    "status": { "state": "TASK_STATE_WORKING" } } } }

Extraits simplifiés, binding JSON-RPC, version 1.0. Même enveloppe que MCP : seules les méthodes et les objets changent.

Le rôle « user » désigne le côté client, que l’émetteur soit un humain ou un agent. Autres opérations : GetTask, ListTasks, CancelTask, SubscribeToTask. Le client annonce la version dans l’en-tête A2A-Version.

Suivre une tâche longue

Interrogation

Le client appelle GetTask à intervalles réguliers.

Simple, universel ; latence plus élevée.

Flux

SendStreamingMessage ou SubscribeToTask : événements poussés en SSE.

Retour en temps réel ; connexion à maintenir.

Notification

L’agent distant appelle un webhook fourni par le client.

Adapté aux tâches de plusieurs heures, client déconnecté.

Flux et notifications sont optionnels : l’Agent Card indique ce que l’agent prend en charge.

Les trois mécanismes répondent à des durées de tâche différentes : secondes, minutes, heures ou jours. Un webhook exposé par le client est lui-même une surface d’attaque : il doit authentifier l’appelant.

03Choisir et combiner

Deux protocoles complémentaires, et des questions encore ouvertes.

Environ 10 min. Partie de synthèse et de prise de recul : comparaison terme à terme, architecture combinée, critères pour trancher entre outil et agent, limites ouvertes, puis une question de conception à traiter en binôme pendant 5 minutes.

Une architecture qui combine les deux

A2A traverse les frontières d’organisation ; MCP reste un détail interne de chaque agent.

Relire ce schéma avec les patterns du cours précédent : le superviseur délègue, mais ici les spécialistes sont hors de son processus et hors de son contrôle. L’orchestrateur peut aussi avoir ses propres serveurs MCP. À l’intérieur d’un même framework et d’une même équipe, un simple appel de fonction entre agents reste souvent suffisant.

Outil ou agent : comment trancher ?

Règle du cours précédent, inchangée : commencer par la solution la plus simple qui satisfait le besoin.

La frontière est une décision de conception, pas une propriété technique : un même service de recherche peut être exposé comme outil (requête → documents) ou comme agent (question → synthèse sourcée). Faire discuter la salle sur un exemple : un service de traduction, un service de réservation de voyage.

Limites et questions ouvertes

Sécurité et identité

  • Au nom de qui un agent agit-il, sur plusieurs sauts de délégation ?
  • Une carte ou une description peut mentir : la confiance ne se déduit pas du protocole.

Fiabilité

  • Les erreurs se composent d’un agent à l’autre.
  • Comment évaluer un système dont une partie est opaque ?

Coût

  • Contexte consommé par les descriptions d’outils.
  • Appels LLM multipliés par la délégation.

Maturité

  • Spécifications récentes, ruptures entre révisions.
  • Registres, observabilité et gouvernance encore en construction.
Slide de prise de recul pour le niveau master. Ces questions sont de bons sujets de mémoire ou de veille. Rappeler que les protocoles FIPA ont échoué en partie par excès de complexité : l’adoption se joue sur la simplicité d’implémentation.

Question de conception

Un assistant de veille juridique doit chercher des textes dans une base interne, puis obtenir d’un cabinet partenaire une analyse de conformité.

À décider

Quelles capacités exposer en MCP, avec quelles entrées ?

Quelle tâche déléguer en A2A, et quel artefact attendre ?

À justifier

Quelles données ont le droit de sortir de l’organisation ?

Où placer une validation humaine ?

5 minutes en binôme, puis mise en commun.

Réponse attendue : la recherche dans la base interne est un outil MCP (entrée typée, résultat prévisible, données maîtrisées) ; l’analyse par le cabinet partenaire est une tâche A2A (autre organisation, travail long, précisions possibles). Le choix n’est pas exclusif : l’agent du cabinet utilise probablement ses propres serveurs MCP.

04TP : construire
un serveur MCP

45 min, en binôme. Objectif : compléter un serveur MCP local en stdio et le tester avec MCP Inspector, sans assistant ni clé d’API. Vérifier que chaque binôme a un poste prêt avant de présenter la mission.

Mission : donner accès aux fichiers

En binôme, compléter un serveur MCP local qui expose l’outil lister_dossier.

  • Déclarer la description et le schéma d’entrée.
  • Lister un dossier : nom et type de chaque entrée.
  • Empêcher le serveur de sortir de son dossier autorisé.
  • Tester avec MCP Inspector, sans assistant ni clé d’API.

45 minutes · transport stdio · dossier fictif bac-a-sable/ · dans tp/ : npm install puis npm run inspect.

MCP Inspector joue le rôle de client de test : connexion au serveur local, inspection des outils et des schémas, appels manuels, observation des résultats et des erreurs. Le squelette est dans tp/src (TODO 1 à 4, plus les tests du TODO 5 si le temps le permet) ; les élèves suivent tp/GUIDE_ELEVES.md. La correction est dans tp/correction, avec CORRIGE_TODO.md. Lien direct avec la slide « Une frontière de confiance » : un serveur stdio s’exécute avec les droits de l’utilisateur, c’est donc à lui d’appliquer le moindre privilège. Sous Windows, passer par npm run inspect : lancé directement avec « node », Inspector peut échouer avec spawn node ENOENT.

Évasion../.. ou C:/WindowsAccès refusé

Tester l’évasion avant de la corriger : que voit-on ? Qu’en ferait un modèle manipulé par une injection de prompt ?

Réponses vérifiées avec la correction. Avant le TODO 3, « ../.. » liste les dossiers au-dessus du bac à sable : c’est la faille. La correction refuse tout chemin hors racine, puis revérifie après fs.realpath, car un lien symbolique placé dans le bac à sable peut pointer vers C:/Windows (testé avec une jonction). Toutes les erreurs reviennent comme un résultat isError: true avec un message lisible, pas comme une erreur JSON-RPC : le modèle peut lire le message et corriger son appel. Les erreurs JSON-RPC sont réservées au protocole (méthode inconnue, version non prise en charge). Faire remarquer que les messages ne doivent pas divulguer de chemins absolus de la machine.

Pour aller plus loin : un outil lire_fichier, les fichiers exposés en resources, puis le serveur branché sur un agent Mastra.

Rappeler le piège stdio : aucun console.log sur stdout. L’extension vers Mastra referme la boucle avec le TP précédent : l’agent devient l’hôte, le serveur écrit aujourd’hui devient l’un de ses outils.

À retenir

  • MCP relie une application IA à des capacités : tools, resources, prompts.
  • A2A relie des agents autonomes autour de tâches suivies dans le temps.
  • Les deux se combinent : A2A entre agents, MCP à l’intérieur de chacun.
  • Un protocole standardise l’échange, pas la confiance : validation, permissions et vérification restent à votre charge.
  • Les spécifications bougent : raisonner sur les concepts, vérifier la révision.
Si une seule idée devait rester : un protocole standardise l’échange, pas la confiance. Faire reformuler par un étudiant la différence entre déléguer une fonction (MCP) et déléguer un objectif (A2A). Le dernier point justifie la méthode du cours : les concepts survivent aux révisions, pas le détail des champs.
